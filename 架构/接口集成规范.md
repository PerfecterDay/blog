服务端调用另一个系统的 API，本质上是在自己的业务系统中引入了一条外部依赖链路。生产环境中，不能只考虑如何发送 HTTP 请求，还要考虑：
+ 超时连接复用
+ 重试
+ 幂等
+ 安全
+ 故障隔离
+ 可观测性
+ 资源管理

## 超时
**建议：每个外部 API 都必须有总超时，不能依赖默认值。**

## 连接池
Max Connections	最大连接数
Max Connections Per Route	单个目标地址最大连接数
Idle Connection Timeout	空闲连接保留时间
Connection TTL	连接最大生命周期
Keep-Alive	是否允许复用连接
Validate After Inactivity	连接空闲一段时间后，复用前检查连接状态（取决于客户端实现）

**Idle Connection Timeout 最好小于链路中最短的空闲连接超时时间。**
```
http客户端 IdleConnTimeout：50 秒
F5 Idle Timeout：60 秒
防火墙 Idle Timeout：90 秒
```
这样客户端会优先清理空闲连接。

## 重试
哪些情况适合重试？

异常	是否建议重试	说明
TCP Connect 失败	通常可以	请求通常尚未到达应用
Connection Reset	视情况	需要判断请求是否已经被处理
Read Timeout	谨慎	服务端可能已经执行成功
HTTP 429	可以考虑	遵循 Retry-After
HTTP 502 / 503 / 504	可以考虑	结合业务和错误语义
HTTP 400 / 401 / 403	通常不重试	通常属于请求或权限问题
HTTP 500	谨慎	不代表业务操作没有成功


2. 重试需要控制的参数
- 建议至少包含：
- 最大重试次数。
- 重试间隔。
- 指数退避（Exponential Backoff）。
- 随机抖动（Jitter）。
- 最大重试时间。
- 可重试异常列表。
- 可重试 HTTP 状态码列表。

3. 幂等性设计
对于 POST、支付、转账、账户绑定等操作，建议使用业务幂等键。

## 安全：不要只关注 HTTPS
外部系统调用通常涉及身份认证、数据传输和证书验证。

建议：
1. 正确验证 TLS 证书，不要使用 InsecureSkipVerify=true。
2. 对敏感 API 使用双向 TLS（mTLS）。
3. API Token、Secret 不要硬编码。
4. 定期轮换密钥。
5. 对敏感请求参数脱敏。
6. 防止 SSRF，不允许不受信任的用户输入直接决定请求目标 URL。
7. 对请求来源进行身份认证和权限校验。
8. 防止日志泄漏 Authorization、Cookie、身份证号、手机号等信息。

## 规范
如果要在团队内部制定一套 API 调用规范，我会优先要求：
优先级	规范
P0	所有外部请求必须设置超时
P0	所有 Response Body 必须正确关闭
P0	禁止关闭 TLS 证书校验
P0	非幂等请求禁止无条件自动重试
P0	必须记录请求耗时、目标服务和错误类型
P1	合理设置连接池及空闲连接超时
P1	对重要外部依赖配置熔断和并发隔离
P1	重要业务操作必须具备幂等性
